# Raid Ledger Companion wire contracts

**Owner: Raid Ledger.** The Raid Ledger Companion desktop app (Tauri) and its
Rust collectors (`rl-collectors`) **push** JSON messages to Raid Ledger. Raid
Ledger owns every format in this folder, exactly like LedgerLink and RL
Valheim Link (`CLAUDE.md` → "LedgerLink addon contract"): only a Raid Ledger PR
touching this folder changes a format. The app and the collectors pin a copy
of the `vN/` folders they speak and validate against it in their own CI.
Design background: spike ROK-1951 §3.5 and §5. Story: ROK-1954.

This folder is **new and additive**. `packages/contract/ledgerlink/` and
`packages/contract/valheim-link/` are untouched by it; the Companion contracts
are siblings, not a change to either.

If this prose and the Zod source ever disagree, **the Zod source wins** and the
prose is the bug.

## Contract index

Every message is one envelope ([`envelope/v1/`](./envelope/v1/CONTRACT.md))
whose `contract` + `contractVersion` select an entry in the registry
(`COMPANION_CONTRACTS` in `packages/contract/src/companion-registry.ts`).

| Contract id | Current version | Status | Folder | Zod source |
|---|---|---|---|---|
| *(envelope — not a registry entry)* | `envelopeVersion: 1` | current | [`envelope/v1/`](./envelope/v1/CONTRACT.md) | `src/companion-common.schema.ts`, `src/companion-envelope.schema.ts` |
| `bg3-save` | `1` | `current` | [`bg3-save/v1/`](./bg3-save/v1/CONTRACT.md) | `src/companion-bg3-save.schema.ts` (+ `-raw.schema.ts`, `-normalise.ts`) |
| *(device-link — HTTP link/poll bodies, not a registry entry)* | `1` | current | [`device-link/v1/`](./device-link/v1/CONTRACT.md) | `src/companion-devices.schema.ts` |

Each `vN/` folder holds `CONTRACT.md` (normative prose), `schema.json`
(generated JSON Schema, draft 2020-12), `CHANGELOG.md` and `fixtures/` (valid
cases, plus `fixtures/invalid/` with an `EXPECTED.json` mapping each case to the
Zod issue `{ path, code }` it must raise).

Regenerate every `schema.json` file, from the repo root:

```
npm run build -w packages/contract && node packages/contract/scripts/gen-companion-schemas.mjs
```

The api jest spec `api/src/companion/companion-contract.spec.ts` checks every
fixture and fails CI when a `schema.json` drifts from its Zod source.

## Rules shared by every Companion contract

1. **Strict keys.** Every wire object is `.strict()`: an unknown key anywhere
   rejects the whole message. The only loose schema is a collector's *input*
   (for example Larian's `SaveInfo.json`), which is never on the wire.
2. **The server ships first.** Because every object is strict, a new optional
   field is released in the Zod source and `schema.json` (and deployed) before
   any app or collector may emit it. A client that emits a field the deployed
   server does not know is rejected.
3. **Additive vs breaking.** *Additive* (stays `vN`): a new optional field the
   server can ignore, a new value in a closed **client→server** enum, a new
   ingest error code (the app MUST treat an unknown code as a generic terminal
   4xx), a new registry contract, or relaxing a refinement. A new value in a
   **server→client** enum the app pins (for example the ack `status`) is
   breaking. *Breaking* (new `vN+1/`
   folder): renaming or removing a field, making an optional field required,
   changing a type, unit, range or enum spelling, tightening a refinement, or
   changing the transport. During a breaking transition the server accepts the
   current **and** the previous version (registry status `accepted`); the old
   one is retired only after the operator confirms the app has shipped the new
   one. Every PR touching this folder says **additive** or **breaking** in its
   body and adds a `CHANGELOG.md` entry.
4. **Fixtures are anonymised only (operator ruling 5, 2026-10-24).** A fixture
   built from a real capture is committed only as **anonymised JSON** (the
   exact transform is recorded verbatim in that contract's `CONTRACT.md` →
   Fixtures) plus a **synthetic placeholder image** generated by a committed
   one-liner. A real screenshot or thumbnail **never** enters the repo, nor do
   real names, account ids, GUIDs, world coordinates, file paths or raw save
   folder names.
5. **Display tables are not wire.** Lookup tables that turn engine ids into
   labels (for example `BG3_LEVEL_DISPLAY` in `src/companion-bg3-display.ts`)
   are absent from `schema.json`. Editing them needs no version bump and no
   `CHANGELOG.md` entry. Wire fields stay open, bounded strings so an id the
   tables do not list is never a breaking change.
6. **Never send raw identifiers that could name a person.** Where a contract
   needs a grouping key derived from something the user named (a save folder),
   the collector sends a SHA-256 of it, never the raw value.

## Change process

1. A Raid Ledger PR touching this folder is the only way to change a format.
   It updates the Zod source, regenerates `schema.json` and the fixtures, adds
   a `CHANGELOG.md` entry, and its PR body says **additive** or **breaking**.
2. The Companion app and `rl-collectors` request a change through a Raid
   Ledger story; they never change a format on their own.
3. A new contract gets its own `companion/<id>/v1/` folder, a registry entry in
   `src/companion-registry.ts` and a row in the index above.
